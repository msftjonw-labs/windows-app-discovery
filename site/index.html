How to read these numbers

Discovery and sampling

Default: every hourly file of the 30-day window is streamed from GH Archive (raw files, no BigQuery). The population is every public repository with at least one qualifying event: issue/PR opened or reopened, issue/PR conversation comment, submitted PR review, or inline PR review comment. Each repository gets the key sha256(seed:repository ID); the smallest keys form a uniform random sample without replacement. GitHub GraphQL then verifies each sampled repository (renames are followed by numeric ID) and supplies metadata and source. Deleted or private repositories are replaced by the next draw. Percentages carry Wilson confidence intervals; with n≈100 the worst-case 95% margin is about ±10 percentage points, and Windows-only metrics have much smaller denominators and wider intervals. If more than 5% of archive hours are unavailable, the run falls back to bounded GraphQL issue/PR search, which is labeled non-representative and reports no intervals.

Human activity approximation

GitHub Bot accounts and logins matching bot patterns are excluded. Unresolved actors are not accepted as human evidence. Ordinary User accounts can still operate automation. Issue activity does not necessarily mean code development occurred.

Static analysis

Snapshots are pinned to the default-branch SHA at scan time. Versioned regex/manifest rules infer platform and framework evidence. Windows candidates are scanned by Microsoft Application Inspector with custom pilot rules (bundled rules disabled). No repository code or build scripts are executed. Project findings preserve multiple labels with file/line evidence and qualitative confidence; repository summaries can combine signals. Comments and strings may produce false positives. Absence of a match is not proof of non-use.

Denominators and exclusions

Platforms, languages, and frameworks use complete scans only and assign each repository to exactly one category, so each chart sums to 100%. Every detected signal remains listed per repository. Windows candidates contain both “Windows” and “Multiple OS (incl. Windows)”. Windows application types and components use complete Windows scans with an explicit application indicator. Partial, failed, and no-eligible-source inventories are excluded from headline distributions. A no-eligible-source inventory is not a complete code scan and is shown separately. Zero eligible repositories displays “N/A,” not 0%. Test, sample, generated, vendored, build, and selected dependency directories are excluded. Lock files and known generated artifacts, documentation, datasets, test fixtures, and non-manifest JSON/text assets are outside the declared source scope. Supported source files up to 8 MiB are decoded as UTF-8, BOM-marked UTF-16/UTF-32, or recognizable BOM-less UTF-16, then normalized to UTF-8. Symlinks and submodules are out of scope and never followed. Oversized source archives use bounded GitHub GraphQL blob batches (up to 10,000 files, manifests first), with pinned raw-byte retrieval when GitHub cannot return exact text. Skipped large source files, unsupported encodings, truncated trees, or file/byte retrieval limits make a scan partial. Inspector timeouts, errors, and skipped source also make a scan partial; detected findings are retained, never treated as proof of a complete scan. Forks are retained and labeled, so repositories are not independent applications.

Component adoption = repositories with a detected component ÷ eligible Windows application repositories. This is the equal-weighted average of per-repository detection indicators, not percentage of source lines or runtime calls. Native/Win32 does not prove a GUI; “console / other / unknown” is deliberately unresolved. No accuracy benchmark has yet established precision or recall.
